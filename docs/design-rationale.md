# Design rationale

Nightweaver addresses recurring failure modes in long-running coding work. Verify the exact project and version, pass the next agent the goal and the real failure, and make every advancement traceable to its evidence.

| Failure mode | What Nightweaver does |
| --- | --- |
| Several sessions or replicas are working on different versions of a project | Bind a project name to a canonical checkout and reject a mismatched clone. Pin the exact source and base when registering each run. Serialize linked checkouts via their shared Git directory and advance result branches atomically. |
| A worker says it finished, but no result can be reproduced | Run operator-authored checks against the staged implementation and detect tracked changes during checking or review. Record the exact tree, exit code, log and artifact hashes. |
| An agent fixes an assertion instead of fixing the product | Support tracked protected paths and optional tracked edit allowlists. Store the check commands in the run plan, outside the worker's checkout. |
| A browser flow works while the interface still looks wrong | Let the project require fresh screenshots and an independent review decision. Feed an actionable `REVISE` result into the next worker attempt. |
| A long tool call times out or the control surface closes | Keep the run independent of the dashboard. A dispatcher can recover enrolled runs at Windows sign-in and preserve the worktree, logs and repair budget after interruption. |
| One agent or session loses the original goal | Give each worker the objective, acceptance requirements, previous accepted commits, current check commands, and latest failure. Final checks verify the completed result against whole-project requirements. |
| A run ends when its plan runs out, not when the goal is met | With `pursue`, the finished build is judged by an independent model against the goal and criteria, using one fixed rubric and never the pass mark. The controller first re-runs the checks that apply to the finished build, so the judge reads fresh evidence, and a judgment that would finish the run is confirmed by a second one. Further waves are planned from the judged gaps. The best build is kept, with green builds ranked first, a losing wave is reverted and every stop has a typed reason. |
| The first build sets a look that later waves only polish, or a stalled score is repeated by the same kind of wave | `pursue.explore` builds several divergent versions of milestone 1 and keeps the winner. `pursue.rescue` diagnoses a plateau, builds divergent strategies from the best build and keeps one only if the judge prefers it in both orders. Both are bounded, and the judge route stays read-only. |
| A browser check shows only the first load of a page | A browser gate can click the page's controls itself and photograph each state. Writes and cross-site navigation are answered locally while it runs, and destructive controls are skipped. |
| Worker-written test code reads a credential from the environment | Gates, git and `command` routes run with every credential-shaped variable removed. Each model process keeps only its own vendor's credentials, and an unattended Claude route runs in Nightweaver's own config directory. |
| A run stops overnight and nobody knows | Opt-in ntfy notifications cover every way a run stops unattended, with quiet hours and a morning digest. |
| A local model approves a broken result | Gate promotion on command checks and any required reviewer verdict. Store local Ollama output as advice. |
| Multiple CLI accounts or model subscriptions are in use | Report the selected provider, profile and model for each role. Offer a live model request before execution and classify recognized authentication, subscription, model access and usage errors during a run. |

## Current limits

- The dispatcher runs one queued job at a time. Prerequisites wait for existing runs to finish, and projects keep their own result branches and pinned baselines. Automatic restart at sign-in requires installing the scheduled task.
- Each attempt has a timeout and each milestone has an attempt limit. Optional run budgets persist across restarts. Token accounting depends on reported telemetry and is not a billing cap. A blocked run stays inspectable and can be explicitly retried without refilling its run budget.
- Recognized provider failures can use an explicitly configured fallback route. Temporary service failures have bounded durable retries. A usage limit parks the run until the provider's reset time, within `retry.max_parks` and `retry.max_park_seconds`, and a reset after the run's time budget blocks it. Without an available fallback, authentication failures block with a login recovery message.
- Git links, allowed tracked paths and Job Objects provide ownership and recovery boundaries. They do not sandbox arbitrary user-supplied executables. Use trusted checks, working directories, adapters, and project content.
- Declarative browser gates cover local static pages, existing loopback apps and owned application servers, responsive viewports and interaction assertions. Screenshots and traces preserve failed attempts as well as successes. The project supplies selectors, any dependency preparation, a trusted startup command and the visual brief; screenshot presence alone is not visual acceptance.
- Git tracks accepted source code. Untracked local state, web deployments, and physical-device or production behavior require explicit project checks and separate operational steps.
- Goal pursuit is only as good as its judge. The judge scores the build from source, check logs and screenshots in one call. Every judge scores against one fixed rubric and is never told the pass mark, and a finishing judgment is confirmed by a second call, but both are language-model calls. The score depends on the judge model and is not calibrated to the owner's taste. Keep-best compares absolute scores from separate calls, not the new build against the previous best side by side. Pairwise judging in both orders is used only for design directions and rescue strategies. The best web judges in one study agreed with humans 70.3% of the time, against 84.6% between humans ([WebDevJudge](https://arxiv.org/abs/2510.18560)). A judge from the worker's own vendor is less independent. The default confirmation uses the judge's own route, so it guards against one noisy call but shares that model's blind spots. A judge told the pass mark returned it in the live trial, which is why no prompt shows it, but an unanchored score is still an opinion. The re-run checks, the target score, the confirmation and the keep-best revert limit the damage from a wrong score. They do not turn it into a measurement. Read a high score as the judge having stopped finding gaps.
- Screenshots are stills. A browser gate shows each page as first loaded, and with a sweep it also shows the states a click reaches. Motion, transitions and timing are judged from source, logs and measured facts, not from what a visitor would see. The judge sees at most 12 screenshots. The sweep only clicks and selects: it does not type or drag, it stops at its control limit (8 by default) or a 45-second budget, and it leaves alone anything named like a delete, purchase or submit. In the live trial the judge saw two screenshots.
- The evidence ledger re-runs the checks that apply to the finished build on each judged build: the plan's checks, its final checks and the checks retained from earlier milestones. Every later wave must keep those passing. That catches regressions. It also means a wave that deliberately changes behavior a retained check asserts will fail the ledger, and a pursuit cannot finish while any ledger check fails.
- A parked runner that was started inline holds the repository lock while it waits for a usage reset, so other runs on the same checkout queue behind it.
- Several detectors are heuristics. Whether a new repository's goal is a web page is a keyword match on the objective's first sentence, so an unusual phrasing reads as not a page and needs `--web`. Whether a repository has tests discovery cannot run, and whether a page can be shown by a bare file server, are decided from file names and a few patterns. Tool droppings are recognised by name (`debug.log`, `chrome_debug.log`, `*.dmp`, `.playwright-mcp/`), so any other stray file still counts as a change.
- Credential scrubbing works by variable name. A secret in a file, a credential helper or a variable with an unremarkable name is not removed, and a check that needs a credential from the environment will not find it. Scrubbing does not sandbox gates: they still run with the operator's permissions.
- Claude routes use Nightweaver's own config directory only with a long-lived token and only when the route sets no `profile_dir`. With a CLI login they use the default profile, so the operator's interactive configuration applies. The idle watchdog's 900-second default applies to plans written by 0.19, and a saved 0.18 plan keeps its original behavior until it sets `budgets.idle_timeout`.
- Served-model logging records a mismatch between the requested and the served model, and only for a route that names a model. It does not change the route or stop the run, and a provider that reports no model in its logs shows none.
- Notifications use ntfy topics with no password, so anyone who knows a topic name can read it. The names are random and `setup --rotate` replaces them, but a public server still carries the messages. The decision inbox is library code: no run asks the owner a question, and the design-direction tournament's owner choice is not connected to it, so the judge always picks the direction.
- Exploration and rescue build their candidates one after another and only at milestone 1 and at a plateau, which costs worker time and judge calls (six judge calls for three passing directions). Parallel candidates and best-of-N selection on every milestone are not built. No controlled study found shows divergent drafts beating one draft plus critique. Neither feature has run in a live trial, so their win rates are unknown, and `metrics` reports the rescue's.
- A pursuit costs more than a standalone agent. In the one blind head-to-head, Nightweaver took 4.3 times the wall time and 11.6 times the observed tokens of a standalone Codex build, and 1.2 times the wall time and 2.9 times the tokens of a standalone Claude build. Each wave adds a planner call, a worker call for each milestone, a judge call and a confirmation call. Budgets bound the spend, but token accounting depends on reported telemetry and is not a billing cap.
- The matched evidence is one blind head-to-head on one brief: one build per contender, no repeats, and two LLM judges from the builders' families. Nightweaver's build won every pairwise call it was in and scored 91 against 90.5 and 86 on a fixed rubric, which does not separate it from the Codex build on that rubric. The comparison also mixes orchestration with a second vendor and a reviewer. It is a strong single data point, not a general result. The [0.19 research record](v0.19-research.md) has the numbers, the adversarial review and what was left out.
