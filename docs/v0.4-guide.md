# Nightweaver 0.4

This continuation closes gaps found while using 0.3 for real application checks and comparisons. Existing plans still work. No provider login, scheduled task or project binding is changed by this release.

## Owned browser application servers

A browser gate can launch a trusted application command in the exact candidate worktree. Nightweaver chooses a temporary loopback port, waits for a successful HTTP readiness response, runs the journeys, and stops the owned process tree. Startup failure, readiness timeout, normal completion, failed journeys and abrupt runner death are covered by Windows process-ownership tests.

```json
{
  "name": "Application journey",
  "kind": "browser",
  "timeout": 180,
  "browser": {
    "server": {
      "argv": ["node", "server.js", "--host", "127.0.0.1", "--port", "{port}"],
      "path": "/",
      "ready_path": "/health",
      "startup_timeout": 30,
      "max_log_bytes": 1048576
    },
    "heading": "Prompt Atlas",
    "steps": [{"action": "visible", "selector": "#search"}]
  }
}
```

The command is an executable argument array, not a shell string. Use an explicit PowerShell executable for a script; `.cmd`/`.bat` launchers are rejected. `{port}` is replaced in arguments, and `NIGHTWEAVER_PORT` and `NIGHTWEAVER_HOST` are also supplied in the child environment. The configured app must honor that port and bind to loopback. Nightweaver does not install app dependencies; use a trusted preparation check when needed, preserving lockfiles and ignoring generated files. A reused source checkout's uncommitted dependencies are not copied into candidate worktrees.

Choose exactly one of `page`, `url` or `server`. The existing `url` mode still targets an operator-managed local app; `server` is the mode that launches from the verified candidate. A managed server uses a fresh port and does not intentionally reuse or terminate an existing development server. Readiness requires HTTP 2xx; redirects are not followed. The outer gate timeout includes startup, journeys and cleanup. Server stdout/stderr remains in private `server.log` evidence; the worker receives a bounded, redacted error excerpt on failure.

Navigation now defaults to the browser's `load` event so applications with persistent connections are not forced to become network-idle. Set `wait_until` to `domcontentloaded` or `networkidle` explicitly when appropriate. Locator assertions and declared journeys establish readiness for dynamic UI. This is functional/layout verification; aesthetic judgment still needs a visual brief and review.

Design reference: [Playwright's web server lifecycle](https://playwright.dev/docs/test-webserver), adapted to Nightweaver's native Windows Job ownership and executable arrays.

## Direct standalone comparisons

```json
{
  "name": "Search comparison",
  "repetitions": 3,
  "tasks": [{"name": "Search contract", "plan": "plan.json"}],
  "contenders": [
    {"name": "Codex standalone", "mode": "standalone", "worker": {"kind": "codex"}},
    {"name": "Claude standalone", "mode": "standalone", "worker": {"kind": "claude"}},
    {"name": "Nightweaver Codex + Claude review", "worker": {"kind": "codex"}, "reviewer": {"kind": "claude"}}
  ]
}
```

`standalone` launches one native Codex, Claude, Gemini or DeepSeek adapter invocation with the complete objective, every milestone instruction and the same acceptance checks. The CLI can use its own tools and internal iterations. Nightweaver performs the final evaluation but supplies no repair calls, provider fallback, independent reviewer or local advice. This measures the configured headless CLI under Nightweaver's evaluation environment, not every possible interactive configuration of that product.

Both `standalone` and `external` now preserve all milestone instructions; 0.3's external collapse retained only the overall objective. They enforce one attempted outer invocation across restarts and explicit retries. An interrupted single-invocation run cannot receive a fresh budget by resuming it. Create a new, labeled experiment when rerunning after account or infrastructure repair; keep the original record. `external` still requires a trusted command wrapper for a complete system such as AGTX. No built-in AGTX wrapper or measured AGTX result is claimed.

## Reproducible starter

```powershell
python examples/create_comparison.py C:\Experiments\search-comparison --repetitions 3
python -m nightweaver --home C:\Experiments\search-comparison\runtime benchmark create C:\Experiments\search-comparison\suite.json
python -m nightweaver --home C:\Experiments\search-comparison\runtime benchmark run BENCHMARK_ID
python -m nightweaver --home C:\Experiments\search-comparison\runtime benchmark report BENCHMARK_ID --output C:\Experiments\search-comparison\report.html
```

The generator refuses to overwrite an existing folder. It creates a tiny isolated search library, protected checks, Unicode/whitespace normalization and matching/ranking milestones, and three contenders: standalone Codex, standalone Claude and Nightweaver with Codex plus Claude review. Creation consumes no model calls. Running consumes the configured CLI accounts' usage. Each task has a six-minute elapsed budget and a two-minute per-invocation timeout. `--codex-model`, `--claude-model` and `--claude-profile` select explicit routes; omitted models use CLI defaults. Record actual CLI/model versions and account readiness alongside any serious experiment.

The starter is a smoke experiment, not a representative benchmark. Broader claims need varied held-out tasks, repeated runs, frozen models/dependencies, equal declared resource limits, comparable permissions and human/visual assessment where relevant. The instruction to leave changes uncommitted applies equally to all contenders.

## Honest result accounting

Reports include per-task summaries, aggregate results and matched outcomes keyed by task, repetition and pinned Git baseline. Every planned run stays visible.

- `accepted`: completed all required checks/review.
- `rejected`: exhausted its repair allowance after an unacceptable result.
- `budget_exhausted`: could not finish within its recorded limits.
- `provider_blocked`: authentication, quota, missing executable or other provider availability problem.
- `execution_blocked`: controller/environment failure prevented evaluation.
- `interrupted`: a single-invocation run was interrupted and cannot be fairly relaunched within its original call allowance.
- `unfinished`: queued, active or paused; not counted as a failure.

`acceptance_rate` retains the 0.3 denominator of all planned runs. `finished_acceptance_rate` uses only done/blocked runs and is null when none have finished. These are operational workflow rates, including account/environment blockers; they do not isolate model capability. Matched pairs containing provider/environment blockers are labeled inconclusive, not wins for the other model. Per-run block reasons remain visible. Interrupted single-invocation runs are also labeled inconclusive when the interruption prevents acceptance.

Observed tokens, missing usage receipts and pending calls remain separate. CLI invocations are not equal units of model compute, and token telemetry is not billing. No automatic winner or statistical significance is asserted. Reports redact common credentials and escape HTML, including benchmark names and block reasons.

Evaluation design references: [SWE-bench](https://github.com/SWE-bench/SWE-bench) for fixed tasks and acceptance, and [promptfoo](https://github.com/promptfoo/promptfoo) for explicit contender matrices. This starter is not a SWE-bench score.
