# Nightweaver 0.19.3 notes

0.19.3 fixes one failure of the `antigravity` provider: an `agy` call that read a file outside its repository ended with no answer, and the run it belonged to never started. It also makes the next failure of that kind say what happened instead of "no answer".

## What happened

A real run on 0.19.2, in a research repository whose objective names files outside it, asked its goal planner (`antigravity`, `gemini-4-neon`, effort `xhigh`, working in a repository on drive D:) to plan. The planner read six files inside the repository, then three more by absolute path in a folder on C:, in parallel. One of the three, step 8, ended with an error:

```
permission check failed for read_file "<path>": user denied permission for read_file(<path>)
Do not attempt to circumvent this denial ...
```

The other two reads, in the same folder and about the same size, completed. The call then ended with status `SUCCESS`, an empty `response`, `num_turns` 1 and `denied_actions: [{"action":"read_file","display_name":"ReadFile"}]`. `agy` also printed one line that is not JSON: `jetski: no output produced — a tool required the "read_file" permission that headless mode cannot prompt for, so it was auto-denied. Add an allow-rule under permissions.allow in settings.json ...`.

Nightweaver 0.19.2 saw an exit code 0, no answer, no refusal under a deny rule and no write. It raised `no_answer`, and the message said nothing about a denial. The initial goal planner (`cli.py plan_goal`) makes one call, so the run was never created.

## Cause

`agy` asks for permission before it reads a file outside the workspace. A headless call cannot answer a prompt, so `agy` denies it on its own ("auto-denied"). It still finishes the batch of tool calls it was in, then makes no further model call, so the turn ends with nothing said. This is not the deny rules Nightweaver passes (those refuse writes, commands and MCP tools, and `agy` words their refusal differently: "Permission denied for ... Matches user-configured deny rule", which does not appear in `denied_actions`). The settings file of a read-only role held only deny rules and nothing that allowed a read, and the worker had no settings file at all.

## What the lab runs showed

Twelve live turns of `agy` 1.5.18 on 2026-11-26, in a scratch repository with a scratch folder beside it, driven with the same flags and stdin as Nightweaver, and five free calls (`/permissions` and `/config` answer without a model turn). The raw outputs are not in the repository; the sanitized captures the tests replay are (`tests/agy_streams`, `reads-01` to `reads-07`).

| Question | Answer |
| --- | --- |
| Does it reproduce? | Yes, on the first try and in five of five calls whose settings did not cover the read, for a read-only role and for the worker. |
| Which read is denied? | The first read in the turn that needs permission, not a particular folder. Reads inside the workspace never need it. The other reads in the same parallel batch complete, but the model never sees them. |
| What fixes it? | `permissions.allow: ["read_file(*)"]` alone (read-only argv with the deny rules, and the worker argv with no deny rules). `"allowNonWorkspaceAccess": true` in the same file also works. |
| Scoped rules? | `read_file(<dir>/**)` did not match. A plain absolute directory (`read_file(D:/some/folder)`, forward slashes, no glob) did, and refused a sibling folder, so a folder missing from such a list costs the whole turn. |
| Do the deny rules still hold? | Yes, with `allowNonWorkspaceAccess: true` beside them a write in the workspace, a write outside it and a shell command were all refused. That probe was not repeated with the `read_file(*)` file. |
| Does resume rescue the answer? | It runs and returns text in the same conversation, but the model holds the denied read as "permission denied" and the other reads of that batch as "canceled": its answer was "unreadable (permission denied); unreadable (canceled); ...". |
| Where do the signals appear? | `result.denied_actions` (a list of `{action, display_name}`, no path, absent from every other result), a `user denied permission for` error on the tool step, and the `jetski: no output produced` line on stderr only. Nightweaver redirects stderr into the same log, so the line lands there before the `result` event. |
| Is the worker affected? | Yes, the same way. Its prose is not read, so it simply stops after the batch and its edits for that turn never happen. |

## What 0.19.3 changes

1. **Every role passes `permissions.allow` for `agy`'s local read tools.** The read-only file keeps all five deny rules and adds `read_file(*)`, `view_file(*)`, `list_dir(*)`, `grep_search(*)` and `find_by_name(*)`. Only `read_file` was ever called in the live runs (the model said it is its only local read tool); the other four load, were in the settings file of the read-only run that passed, and cost nothing. The network and browser tools (`read_url_content`, `search_web`, `read_resource`, `list_resources`, `read_browser_page`) are not in the allow list, which is not the same as being stopped: round 3 found that `search_web` ran in a read-only role and that no rule gates it (see Round 3 review fixes). The rules are not scoped to folders, because a missing folder costs a whole turn and a glob scope did not match.
2. **The worker gets a settings file with the same allow rules and no deny rule.** It keeps `--disable-slash-commands` and `--mode accept-edits` and may edit as before. `invoke()` used to decide "read-only" from `--settings` in the arguments, which would have put the read-only guard and the read-only note on the worker; it now decides by mode, and the worker's prompt is still exactly what the engine built.
3. **A read-only call that `agy` ended silently after an auto-denied prompt is resumed once.** When a read-only role (every role but the worker, `doctor`'s probe included) ends with exit 0 and status `SUCCESS`, no answer, and the stream shows an auto-denial (any of: a tool step with the `user denied permission` error, `result.denied_actions`, or `agy`'s own line), Nightweaver resumes the same conversation (`--conversation <id>`) with every flag of the first call (the `--settings` file, `--mode accept-edits`, `--json-schema` again for a schema role, `--add-dir`) and one short prompt: answer now, in the format the task asked for, from what you have read, call no tool, and say so inside the answer if something could not be read. The first prompt's read-only note comes in front, as on every read-only call. The resumed stream is parsed as the call's answer. The resumed call is resumed once: if it is still empty, it fails as `no_answer`; if it completed a write or asked for one it was refused (or the first call also tried to act and was refused), it fails as `read_only_violation` or `read_only_refused` exactly as a first call would. A call that also tried to act and was refused is not resumed at all, since its answer would be discarded.
4. **The failure says why.** `agy_silence` names the auto-denied actions (`agy auto-denied 1 tool action (read_file <path>)`), quotes `agy`'s own line, says that a headless call cannot answer a permission prompt, says which allow rules Nightweaver passes (or, when the guard saw them missing, that `agy` did not list them), notes that Nightweaver never passes `--dangerously-skip-permissions` (the line advises it), and, after a resume, names the resumed call's log.
5. **The `user denied permission` error is its own class.** It is not a deny-rule refusal (`denied`), not a write (`wrote`) and never raises `read_only_refused` for a read. Any other tool a read-only role was denied this way (an MCP tool, a notebook edit) counts as an attempt to act, like a refusal under a rule. The rule-refusal check runs first, so a refusal that merely echoes the phrase in a path stays a rule refusal.
6. **The guard reports the allow rules; `doctor` warns.** `antigravity_guard` still requires every deny rule loaded and still stops the call when one is missing (`configuration`). It now also reads the allow rules from `agy -p /permissions` (a scope lists them under `allow`) and returns `loaded`, `missing` or `None`; a missing allow rule never stops a call, because it costs answers and not safety. `doctor` shows `read_allow_rules` and warns in plain words when they are missing (a `warning` on a ready live report, text in `action` on the plain one).

## The settings files

Read-only roles (`agy-settings-readonly-<digest>.json`), as first built, with no user rules and no login reads (see Review fixes for what is added):

```json
{
  "permissions": {
    "allow": ["read_file(*)", "view_file(*)", "list_dir(*)", "grep_search(*)", "find_by_name(*)"],
    "deny": ["write_file(*)", "write_file(/)", "write_file(.)", "command(*)", "mcp(*)"]
  }
}
```

Worker (`agy-settings-worker-<digest>.json`), as first built:

```json
{
  "permissions": {
    "allow": ["read_file(*)", "view_file(*)", "list_dir(*)", "grep_search(*)", "find_by_name(*)"]
  }
}
```

## Behaviour per role

| Role | `--settings` | Guard and read-only note | Auto-denied call with no answer |
| --- | --- | --- | --- |
| worker | allow rules only | none | not resumed; its prose is not its product |
| reviewer, judge, replanner, directions, comparison, ranking, diagnosis | allow and deny | yes | resumed once with its `--json-schema`; the structured answer of the resume is the answer |
| planner, brief writer, `doctor` probe | allow and deny | yes | resumed once without a schema; `response`, else the last message with text |

A plain `SUCCESS` with no text and no sign of an auto-denial keeps failing as `no_answer` at once. The facts do not show that a resume rescues a call that was silent for another reason, so none is tried. What counts as a sign, how much time a resume gets and which text is not an answer were tightened in round 2 (see Round 2 review fixes).

## How the two calls are recorded

The first call keeps its log. The resumed call writes its own, `<log>.resume.jsonl`, beside it (`call.jsonl` and `call.jsonl.resume.jsonl`). A log written again first removes a resume log left by an earlier attempt. The call's usage is the sum of the two calls' own usage, each read from the steps of its own stream (the result's `usage` is cumulative over a resumed conversation, so adding the two results would count the first call twice; the lab's pair was 12,854 and 2,806 tokens, and the resumed result said 15,660). The receipt the engine records for the call gains `resume_log`. The resumed turn counts in the observed tokens but not as a second provider call against `max_calls`, and it may take up to the call's timeout again.

## Limits

- **The allow rules open reads everywhere the account can read, except what the Review fixes deny.** `read_file(*)` has no folder scope, so a read-only role (and the worker) can open any file on the machine that is not one of the login places, a plan's profile, key or token file or a rule of the user's own. The deny rules still refuse writes, commands, MCP tools and (round 3) the two URL classes `agy` documents, but `search_web` is not stopped by any rule, so what a model reads can leave the machine in a web search query as well as reach Nightweaver through its answer; a completed search or URL read is recorded as a warning event (Round 3 review fixes). Agy's own guidance for model-written grants says never to use `read_file(*)`; this is a grant Nightweaver writes in a file it controls. A tighter form is one plain `read_file(<absolute folder>)` per folder the call may read, but a folder missing from the list costs the whole turn, so it is not used. `"allowNonWorkspaceAccess": true` also fixed the reads in the lab and is a broader switch whose name speaks of non-workspace file access in general; it was not used.
- **Whether agy's protections for sensitive files (`.env`, SSH keys, `.git`) hold under these rules was not tested.** The 1.5.18 changelog says they do. No real secret was allowed near `agy`.
- **A rule that loads is not a rule that matches.** `/permissions` listed every candidate the lab tried, including a glob that never matched. The guard proves the file reached `agy`; only a live call proves a read is allowed or denied (the live calls of this release are below, and Round 2 ran the read denies).
- **The resume is a net, and the allow rules are the fix.** In the one real resume (the lab's `reads-02`) the model had read nothing it could use from the denied batch and answered "unreadable", so a resumed answer may only say that. The prompt asks it to say so inside the answer instead of guessing. A schema role gets a structured answer even then, so a resumed reviewer or judge verdict can rest on reads that never reached the model; the log pair shows when that happened (the `<log>.resume.jsonl` file exists, and the receipt names it). A resume that is allowed to read again was not tried.
- **Only the first read that needs permission in a parallel batch is checked.** Whether that is intended is not known. It is why one rule or one denial decides a whole batch, and why a scoped rule cannot be tested with several reads in one step.
- **The second wording of agy's line was never seen live.** `agy.exe` also holds "the %s tool(s) required approval that headless mode cannot prompt for, so they were auto-denied. Settings allow-rules do not apply; ...". Detection keys on the phrases the two share between them and on the other two signals, and any one is enough.
- **Not run:** the write and shell probe with the `read_file(*)` settings file (the deny rules are class-based and independent of the allow rules, and the live read-only call below completed no write), `--dangerously-skip-permissions`, other models or efforts, and agy versions other than 1.5.18. One host, one account.
- **The detection is by wording where the stream gives no structure.** `result.denied_actions` has no path and no count, so the named actions come from the tool steps when there are any.

## Review fixes

A review of this branch ran the real `agy` 1.5.18 with free calls only (`/permissions` and `/config` answer without a model turn) and found two problems. The same change made both real: before `read_file(*)` the permission prompt stood between a model and any file outside the workspace, and now only the rules do.

### 1. A user's own deny rules were silently replaced (confirmed)

`--settings` replaces `permissions.allow` and `permissions.deny` of the user's own `settings.json` as whole lists; it does not merge them. With the home pointed at a scratch folder whose `settings.json` held two deny rules (a private folder and `read_file(**/.env)`) and one allow rule (`command(git status)`):

| Call | What `agy -p /permissions` listed |
| --- | --- |
| The user's file alone (control) | the user's three rules |
| 0.19.3 as first built, the read-only file beside it | the five allow and the five deny rules of the file; the user's two deny rules were gone (`/config` showed `permissions` as exactly the file's object) |
| 0.19.3 as first built, the worker file | the user's deny rules survived (the file had no deny key); the user's allow rule was replaced by the five allow rules |
| With this fix, the read-only file | the five allow rules; the five deny rules, the login-read rules (below) and the user's two deny rules |
| With this fix, the worker file | the five allow rules and the user's allow rule; the login-read rules and the user's deny rules |

0.19.2 dropped the same rules, but with no read grant an outside read was auto-denied anyway. With `read_file(*)`, a dropped user deny rule is a read the user had refused, for the reviewer, judge, planner, brief and probe roles. The worker's dropped allow rule was a regression of its own: before 0.19.3 the worker ran under the user's rules, and a command they let it run now stopped at a prompt, which is the silent end this release fixes.

The fix reads the user's `permissions` (strings in the two lists only; anything else, an unreadable file or a missing one adds nothing) and writes the union, Nightweaver's rules first and repeats once:

| File | `allow` | `deny` |
| --- | --- | --- |
| Read-only roles | the five read tools | `AGY_DENY`, the login reads, the user's deny rules |
| Worker | the five read tools, the user's allow rules | the login reads, the user's deny rules (none of `AGY_DENY`: it may edit) |

The user's allow rules are not added to the read-only roles: a grant of the user's (`read_url_content(*)`, say) must not widen a role that reads files a prompt-injected repository controls, and a user deny rule cannot be overridden by an allow rule. The name of each file carries a digest of its content (`agy-settings-readonly-<digest>.json`), because the content now depends on the user's file and on the plan: a fixed name would let one plan's call rewrite the file another plan's call was about to start with. A change in either moves the next call to another file, and the one a running call started with is not rewritten.

Not covered: the project and shared scopes of `agy`'s own settings (where `agy` keeps them was not found and whether `--settings` replaces them was not tested; on the machine of the round 2 live calls the shared scope listed six `command(...)` allow rules of the user's own beside the generated file's global rules, so `--settings` does not remove that scope, and whether the generated `command(*)` deny beats a shared allow was not isolated), and a listing check for the user's rules: the guard still requires only `AGY_DENY`, because a rule `agy` writes back in another form would otherwise stop every call with a misleading `configuration` error.

### 2. `read_file(*)` handed Nightweaver's key and token files to a model (confirmed)

The review reported a live turn (the real read-only argv and file in a scratch workspace) that read a file outside the workspace and the workspace's `config.json` through `read_file`, so any readable path was allowed; the first build's file holds no read deny rule at all, which this branch's code and the two live checks above show without a new model call. A prompt-injected file in a repository could have had a model read a key or token and put it in its answer, which Nightweaver stores (`redact()` knows only token patterns). 0.19.2's auto-denial had been the only barrier. The review also reported that a deny rule wins over an allow rule in the same call (a live turn; not repeated here, since this round allowed no model call), so the fix is deny rules, now that the user's own are no longer replaced.

Every read tool of `AGY_ALLOW` (`read_file`, `view_file`, `list_dir`, `grep_search`, `find_by_name`) is denied at these places, in both files, as `tool(<absolute path with forward slashes>)`, the form the live runs matched:

- Nightweaver's `providers.json` (it names the DeepSeek key file) and its `profiles` folder (the Claude and DeepSeek profiles Nightweaver keeps).
- The DeepSeek key file that `providers.json` or `DEEPSEEK_API_KEY_FILE` names.
- The login file of each CLI Nightweaver drives, in its default home or the one the environment chooses: Claude's `.credentials.json` (`CLAUDE_CONFIG_DIR` or `~/.claude`), Codex's `auth.json` (`CODEX_HOME` or `~/.codex`) and Gemini's `.gemini/oauth_creds.json` (`GEMINI_CLI_HOME` or the home). Only these files, not the folders: `agy` and the CLIs keep their work in them.
- Every `profile_dir`, `api_key_file` and `oauth_token_file` anywhere in the plan a run or the goal planner works on. A run registers them when it is opened (`Run`), the goal planner when it has read its template (`plan_goal`, after the paths are made absolute), through `providers.protect()`. The doctor probe, a brief writer and any process that has opened no plan know only the first three groups.

Nightweaver's home as a whole is not denied: `runs/<id>` in it holds the worktrees and the evidence a review reads, so a deny on it would deny the review. For the same reason a place that holds the repository, the run's own folder, or `runs` (a `profile_dir` that is Nightweaver's home or a parent of it) is not protected.

What this proves and what it does not: the rules load. A free `/permissions` listing printed the user's and the generated rules unchanged, paths with spaces, parentheses, brackets and non-ASCII characters included. That a deny rule on a plain absolute path matches the files under it, and wins over `read_file(*)`, was not run in this round because the review allowed no model call; Round 2 proved it live (below), and also showed `agy` matching the same place spelled with backslashes, another letter case, `..` and through a junction. A glob scope is not used, because one did not match. The notes of the first build said that agy's own protection of `.env`, SSH keys and `.git` was not tested; it still was not (not tested here either: only a made-up key file was used). Any other credential file (SSH keys, cloud credentials, browser stores, a project's `.env`) is not named: a user's own deny rule for it is now kept, and is the place for it.

## Round 2 review fixes

A second review of this branch found three problems in the resume and asked for the read denies to be proven live. Each fix has tests in `test_release_0193_agy_reads` (classes `ResumeTime`, `Narration`, `Trigger`) that fail on the first review-fix commit (`687f4c6`) and pass now; a few more in those classes guard what must not change (a structured answer wins, a call that answered is never resumed).

### 1. The resume had the call's whole timeout again (confirmed)

`invoke()` passed the call's full `timeout` to the resumed call, so a first call that took most of it let the pair run for up to twice the limit. The resume now gets the timeout less the time the first call took (`execute()`'s own time, on the monotonic clock) and is skipped when less than `AGY_RESUME_FLOOR` (20 seconds) is left: the call fails as `no_answer`, and the message says the resume was skipped for lack of time and how many seconds of the timeout were left. Exactly the floor still starts the resume. The pause check and the health limits (`idle_timeout`, heartbeat, log-size limit) reach the resume as before. A resumed model turn took 39 s in the lab (effort low), so a resume started with little more than the floor can still be ended by the clock; it is then reported like any call the time limit ends, as a controller exit and not as a provider failure.

### 2. Narration before the denied batch was taken for the answer (confirmed)

`response` joins every agent message of the run, so a model that wrote "I will read the files" before its reads and was then auto-denied had `response` equal to that sentence, and the call counted as answered: no resume, and the sentence went on as a plan or a verdict. None of the lab's denied calls had such text (the model said nothing before its reads), so this was read from the stream's structure and the captures are the lab's with messages written into them. When the stream shows an auto-denial, the agent messages that came before the denied tool batch are narration: the call has no answer, so the resume applies, and the failure says so (`Its 2 agent messages with text came before the denied tool batch, so they are narration and not an answer.`). The batch is the last auto-denied tool step; when only the result's `denied_actions` or `agy`'s line shows the denial, it is the last tool step. (Round 3 changed this: the batch ends at the last tool step of the call whichever step was denied.) A message after the batch is a real answer and is kept alone (not the joined `response`), a message whose step index is unknown is never discarded, and a schema role's `structured_output` still wins. The worker's returned text follows the same rule.

### 3. The resume fired on any of agy's phrases (confirmed)

`agy_auto_denied` took any non-JSON line that held `no output produced`, `auto-denied` or `cannot prompt for` as a denial, so a call that ended with no output for another reason was resumed and described as an auto-denial. A denial signal is now one of three things: `result.denied_actions` not empty, a tool step that ended with `user denied permission`, or `agy`'s own line when it also names a permission (`permission` in the line: the first wording has it, the second has it inside `--dangerously-skip-permissions`). A bare `no output produced` line for another reason, or an unrelated `cannot prompt for` warning, stays `no_answer`, is not resumed, and is quoted (`agy printed: "..." It does not name a permission, so Nightweaver does not read it as a denied permission prompt and did not resume the call.`). When several lines match, the first that names a permission is the one kept, so an unrelated warning in front of the real line does not hide it. The step error and `denied_actions` fire whatever the line says.

The raw outputs are kept in the lab, not in the repository.

## Round 3 review fixes

A third review of this branch found a way out of the read-only roles that the notes had said did not exist, and three smaller mistakes in the round 2 code. Each fix has tests in `test_release_0193_agy_reads` (classes `DeniedBatch`, `FullLine`, `ResumedLine`, `NetworkRules`, `NetworkEvent`).

### 1. A read-only role could send what it read out through a web search (confirmed)

In the round 2 call that was meant to be a free listing (`r2-exp-01`), the model, under the generated read-only file, read three of `agy`'s own help files and then ran `search_web`, and that step completed. `search_web` is a network tool. The file allows `read_file(*)` (any local file the account can read) and denied no network class, and the notes said the network tools "are not allowed": they were not in the allow list, but `agy`'s own default let `search_web` run, and no rule stopped it. A repository file that carries a prompt injection could have had a read-only role read a local file and put what it read in a search query.

What the fix does and does not do:

- **Added to the deny rules of every read-only role: `read_url(*)` and `execute_url(*)`**, the two network classes `agy` documents (its guidance for model-written grants names `read_url(<domain>)` and `execute_url(<domain>)`), for every domain. The guard requires `agy` to list them like the other deny rules. The worker's file does not have them: it may use the network.
- **`search_web` cannot be gated by a rule that was tried.** It completed under `search_web(*)` and under `web_search(*)`, with both in the file. That is stated here as a known limit and not worked around: a model in a read-only role can run a web search, and what it puts in the query leaves the machine. The two candidates are not passed (a rule that never matches only looks like a barrier). That no rule could gate it was not shown, only that these two do not.
- **The URL rules were never matched live.** In none of the three calls did `agy`'s model call a URL tool: it answered that `read_url_content` is not in its tool list, with the two rules in the file and without them (the init event's tool list names it). The two rules load (the free `/permissions` listing shows both under the `global` scope) and are `agy`'s documented form, so they are kept as harmless; they are not proven to refuse a fetch.
- **A completed search or URL read is reported.** `agy_stream` returns the completed steps of `search_web` and `read_url_content` in `network` (a denied step did not run and is not in it), and the engine records a `read_only_network` event after the call, naming the steps (redacted, cut to 200 characters) and the log. A read-only call only (never the worker), `antigravity` only. The answer is kept: a search is not a failure, and discarding the answer would not call the query back. Calls made outside a run (the goal planner before a run exists, `doctor`) record nothing, because there is no run to record it in. A denied `read_url_content` or `search_web` stays a harmless read (`denied`, never `refused`), as in 0.19.2, since it did not run.

### 2. The denied batch ended at the denied step, not at the last tool step (confirmed)

Round 2 ended the batch at the last auto-denied tool step when one failed and at the last tool step otherwise, so the stream text@1, read@2, DENIED@3, text@4, read@5, read@6 kept the text at step 4 as the answer and never resumed (`response` joined both texts, and the batch's later reads still ran after the denied one). The batch now always ends at the last tool step of the call whenever a denial is detected, so both texts are narration, the answer is empty and the call is resumed. A message after the last tool step is still the answer, alone.

### 3. The permission test ran on the 600-character quote (confirmed)

`agy_auto_denied` looked for `permission` in the line cut to 600 characters for quoting, so a line that named the permission after character 600 was not read as a denial. `agy_line` now returns the quote and whether the line it read names a permission, `agy_stream` keeps that as `notice_permission`, and `agy_auto_denied` uses it (a hand-made dict without the key is judged on the quote). The test is on the first 4096 bytes of the line, which is all of the line that is read; a permission past that is still not seen (a limit that keeps a huge line to one read).

### 4. A resume replaced the first call's line with any line of its own (confirmed)

After a resume the failure message quoted the first call's line when it had one and otherwise the resumed call's. The resumed call's own line now replaces it only when that line names a permission; otherwise the first call's stays (and the resumed call's is still used when the first printed none).
