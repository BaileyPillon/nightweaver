# Nightweaver 0.19.1 notes

0.19.1 is a fix release. Most of it answers one unattended pursuit, CROW run `002c6a4c577c`, on 2026-11-23. That run built real work, and four separate things stopped it or wasted its time. The Gemini work answers a different problem: the Gemini CLI route did not run on this machine, and Google moved AI Pro and Ultra subscribers to Antigravity. Each section says what happened, what changed and what is still not known.

The tests for all of it use scripted workers, judges and planners, faked gate timeouts and captured or hand-written provider output. None calls a model or the network.

## The run that motivated it

| What happened in run `002c6a4c577c` | Fix |
| --- | --- |
| Blocked at the first promotion because the repository had no git identity | Identity check at launch, fallback identity at commit time |
| A wave's early milestone was given the plan's final-only checks, and the run stuck on them twice | Wave milestones keep final checks off, `settle_gates` for runs 0.19 had already extended |
| A gate with a 120 second limit ran out of time and the run blocked | One retry with twice the time, and a gate that still times out is unscored |
| A 14 hour time budget was spent, about 9.5 hours of it with the run blocked | `max_seconds` counts active time only |

### Git identity

The run stopped when Nightweaver first had to create the accepted commit in the repository. Git had no author identity there and answered "Author identity unknown". Nothing before that point had needed one, so the failure came only after the work that had to be committed.

- `goal` and `add` with `--start` or `--enqueue`, `oneshot` unless `--preview`, and `wish --start` now ask git for `GIT_AUTHOR_IDENT` and `GIT_COMMITTER_IDENT` before any model call. A repository that resolves neither refuses to launch and the message names the exact `git -C <repo> config user.name` and `user.email` commands, quoted for cmd and PowerShell, with a single-quoted PowerShell form for paths holding `$`, a backtick or a curly double quote. `doctor --plan` and `preflight` report the same thing.
- A run that began before the check existed, or whose git configuration changed afterwards, no longer loses its work at promotion. Commits made by milestones, exploration and rescue go through one helper that fills only what git cannot resolve. A role with neither a name nor an email gets `Nightweaver <nightweaver@localhost>`; a role with one of them keeps it and takes only the other half from that pair, so a repository with `user.name` set, no email and `user.useConfigOnly` commits as `Alice <nightweaver@localhost>`. A configured name or email is never overridden. `milestone_accepted` records `identity_fallback` when the fallback was used, and `filled` names the half when a role got only one.

Not known: whether a repository whose identity comes from an `includeIf` or a credential helper outside git's own resolution behaves the same. The check asks git, so it should.

### Wave milestones and the final checks

0.19 gave every milestone of a planned wave the last milestone's checks, including the checks the plan only promised for the finished build (`final_gates`, checks retained `final`, checks only the last milestone owns). A wave of three milestones is meant to build toward the goal, so an early one cannot meet a check such as "every study has `result.json`" when its job is only to freeze the inputs. The run was stopped by this twice, and `--retry` did not help, because the milestones of the waves already planned carried the same list.

- `final_checks` is now written into every pursuit plan. A new wave's milestones get the checks every milestone passes (the plan's `gates` and the checks retained `subsequent`); only the wave's last milestone also gets the final-only ones. A plan whose checks are all final plans one-milestone waves. A one-milestone plan keeps its own checks per-milestone, as 0.19 had it.
- A pursuit made by 0.19 has no `final_checks`. `legacy_final` derives the split from each milestone's `retained_from`. Where 0.19's record cannot tell `final` from `subsequent` (a check owned by the penultimate milestone), it takes the check as final, because a run stuck on a check is worse than a check enforced on a wave's last milestone alone.
- `settle_gates` settles such a pursuit when it starts again, `--retry` included: it records the split and takes the final-only checks off the unbuilt early milestones of the waves 0.19 already planned, so the stuck run resumes. A `gates_split` event says which milestones changed. Milestones that were already built stay as they ran, and a stability batch saved against the old check list is dropped because its samples no longer match.

Not known: how often a plan written by hand marks checks `subsequent` that it meant as `final`. The rule follows what the plan says.

### A gate that times out

The run had a gate with a 120 second limit. The controller ended it at the limit, 0.19 treated that as the end of the verification and the run blocked. A timeout says the check was not given enough time, not that the worker's change is wrong, and a larger repository or a busy machine is the usual reason.

- A gate the controller ends at its wall-clock limit is run again once, in a fresh evidence folder, with twice the time (never above 4 hours). `retry.gate_timeout_retries` (0 to 3, default 1) sets how many times and 0 is the 0.19 behavior: the first timeout blocks, now with the gate, its limit and the advice, which 0.19 left out. The raised limit is kept for the rest of that verification, so the other stability samples and a resumed batch do not pay the old limit again. A proof gate whose run on the baseline commit times out counts. A gate that exits 124 itself, or ends at its log limit, is not retried: only the controller stopping the gate counts.
- A timeout is never a worker failure and costs no attempt. One that survives the retry blocks the run naming the gate, both limits (the one limit when the plan allows no retry) and the way out. A run keeps the plan it was created with, so raising `timeout` in the plan file changes nothing for this run. The advice says to raise `timeout` (up to 7200 seconds) and add the plan as a new run, or to resume with `--retry` if the machine was only busy.
- The judge's evidence ledger re-ran its checks with no retry and counted a timeout as a failed check, which the planner then turned into a "Check failed: <name>" milestone. The ledger now uses the same retry. A ledger check that times out for good is unscored: the run blocks with `blocked_from: judging` and the same advice, no judgment is made and nothing is planned. `--retry` runs the ledger again. The best-build check at the start of a plateau rescue uses the same ledger, so it blocks in `rescuing` the same way.
- A design direction or a rescue strategy whose checks time out for good is recorded as unscored (`direction_unscored`, `rescue_candidate_unscored`, status `unscored`, `passed` null), not as failed. It is left out of the tournament or the comparison with the best build, and `pursuit`, `report` and `metrics` count it apart from the failed candidates, by each candidate's latest build: a block resumed with `--retry` builds them again, and the earlier `direction_unscored` events stay in the log without counting. When every candidate is unscored nothing is known about any of them, so the exploration or the rescue blocks with the advice instead of falling back as if all had failed. The candidates are forgotten, so `--retry` builds them again, and a rescue is not spent. A contest that holds failed candidates as well as unscored ones, with none passing, still falls back as before.

Not known: whether one retry is the right default. Doubling once covers a gate that was a little short; a gate that was an order of magnitude short still blocks, now with the numbers in the message. A candidate that is rebuilt after a block pays its worker call again.

### The time budget

The run had a 14 hour `max_seconds`. About 9.5 hours of it went by with the run blocked, waiting for a person, and the budget counted all of it. That is about two thirds of the budget spent while the run could do nothing.

- `budgets.max_seconds` is now active time: the time since the run started less the stretches it sat blocked or paused. The state keeps a ledger of those stretches (`paused_seconds`, `idle_since`), which every writer of state or pause settles inside its transaction, so the ledger and the phase cannot disagree.
- Time parked on a usage limit still counts. The run is waiting on its own clock, by design, and `park_plan` refuses a wait that would outlast the budget.
- A run made by 0.19 has no ledger. The first writer to reach it reads its blocked and paused stretches from its events once and records an `active_time_derived` event. `budget`, `metrics` and the budget report show active, idle and wall time side by side.

Not known: a run that is blocked for a reason it could have cleared itself, such as a provider that is down for hours, now also spends none of its budget while blocked. The budget bounds work, not the time a run is allowed to exist.

## `goal` and `oneshot` from a file

The Windows command line holds at most 32,767 characters, so a long objective could not be passed. `goal` and `oneshot` take `--objective-file PATH`, a UTF-8 file of up to 1 MB with a BOM or CRLF line ends tolerated. It cannot be combined with the objective argument, and an empty or unreadable file is refused with its path.

## Gemini CLI and Antigravity

### The Gemini CLI route

The `gemini` kind did not run on this machine. On Windows the npm launcher is `gemini.cmd`, and the package's real entrypoint is the `bin` entry of its `package.json` (`bundle/gemini.js` in 0.70, `dist/index.js` in older packages), found beside the launcher. Nightweaver now runs that entrypoint under node with no shell. It sets `GEMINI_CLI_TRUST_WORKSPACE=true` for the call, because a headless run in a folder the CLI does not trust exits at startup, and a Nightweaver worktree never is trusted. An explicit `GEMINI_RESTRICTED_MODE=true` is left alone and blocks the route with that cause named.

Failures another attempt cannot fix are recognized from the CLI's exit code and text and no longer use up repair attempts: exit 41 and "Please set an Auth method", exits 52 and 55 (an untrusted folder, a configuration error), an invalid key, `PERMISSION_DENIED` and a 404 model block the run with the remedy; "exhausted your capacity", a daily quota, `RESOURCE_EXHAUSTED` and a 429 park it until the reset the message names. `doctor` shows how the route will sign in (`auth`) and never the secret. The CLI's Google-account login has been Enterprise-only since June 2026, so the route signs in with a paid `GEMINI_API_KEY` or Vertex.

### Why Antigravity

0.70.0 of the Gemini CLI does not support the Gemini 4 models and has no reasoning-effort setting, and Google moved its AI Pro and Ultra subscriptions to Antigravity. Google's supported route to Gemini 4 Neon at a chosen reasoning level is the Antigravity CLI, `agy`. Nightweaver has a new `antigravity` kind for it, usable wherever another worker, reviewer, judge or planner kind is.

- **Effort per model.** `effort` is checked when the plan loads, against what `agy models` listed on agy 1.5.15 (2026-11-23). Gemini 4 Neon and Hydrogen take `low` to `xhigh`; Carbon, Argon and the 3.x Flash models take `low` to `high`; Gemini 3.1 Pro takes only `low` and `high`; no listed model takes `max`. A route that names no model gets agy's default, `gemini-3.1-pro`, and is held to its levels. A model slug that names its level (`gemini-4-neon-xhigh`, in any case) cannot be given a different `effort`.
- **Vendor family and credentials.** `antigravity` and `gemini` are one family, Google, so a worker of one with a reviewer or judge of the other records `independence_degraded`, and both keep the `GEMINI_*` and `GOOGLE_*` variables and no other vendor's.
- **Modes and input.** (Replaced in 0.19.2: every role runs `--mode accept-edits`, and the read-only roles add deny rules. See [the notes](v0.19.2-notes.md#the-mode-of-each-role).) The worker runs `--mode accept-edits`; every read-only role runs `--mode plan` and does not pass `--disable-slash-commands`, because agy applies plan mode through slash command expansion (with the flag, agy 1.5.15 warns that plan mode has no effect and runs in its default request-review mode). The task goes in on stdin as one stream-json user message, because `--print` ignores stdin and `--input-format stream-json` rejects a prompt on the command line.
- **Sign-in.** Install agy, launch it once and sign in; Neon needs Google AI Pro or Ultra. The installer does not add `agy.exe` to `PATH`, so Nightweaver looks in `%LOCALAPPDATA%\agy\bin` first. A signed-out agy prints a sign-in link and waits about a minute for a code that no unattended run can give, so Nightweaver asks `agy models` before each call (a success is remembered for five minutes) and blocks as `authentication` when agy is signed out. An API key works only with `"modelProvider": "gemini"` in agy's own `settings.json`; the variable alone is ignored, and `doctor` reports `api_key_ignored`.
- **Errors.** agy's own error forms are classified: the `AGY_ERROR` result, "Error 429/403/404/50x", capacity and quota wording, 403 `PERMISSION_DENIED` as a model-access problem and `invalid model selection (...)` as a model or configuration problem, each quoting agy's words.

### What is still unverified

> **Update, 0.19.2.** The first signed-in `agy` runs have been made. The success half of the stream (the answer text, `structured_output`, token counts) and the served-model check are verified; plan mode was seen end to end and then replaced, because it is not a barrier and can answer with a plan file; images and the gaps in error wording are still open. [Item by item](v0.19.2-notes.md#what-0191-listed-as-unverified). The list below is kept as 0.19.1 wrote it.

- **A successful agy run.** The init, step and error-result shapes in the parser's tests were captured from agy 1.5.15 (a call that failed on a rejected key and a refused model). No signed-in run has produced a success, so the success half of the stream-json schema (the answer text, `structured_output`, token counts) was written from agy's documentation, changelog and help text. The parser is one function, `agy_stream`, with fixture tests.
- **The served-model check** for the antigravity kind depends on that same output and is unverified with it. Its model-name matching (`gemini-4-neon` and `gemini-4-neon-xhigh` as one model) was written from the slugs `agy models` printed.
- **Plan mode in a headless run** has not been seen end to end. Nor has anything else that needs a successful call, such as the structured answers of the reviewer, judge and planner roles and token counts.
- **Images.** agy has no image attachment option. A judge or reviewer sees an image only as a path in its prompt that its file-reading tool opens from an added folder, and nothing verifies that it did.
- **Error wording.** Both routes classify failures by exit code and text. A wording that agy or the Gemini CLI changes, or one this release did not see, is an ordinary provider failure until it is added.
- **Gemini 4 on the Gemini CLI.** There is none at 0.70.0, so a route that needs Gemini 4 goes through `antigravity`.

(0.19.2 settled the first two; see above.) Until a live run settles the first two, start with `python -m nightweaver doctor --planner antigravity --live` and treat structured answers, token counts and the served-model check on this kind as unverified.
