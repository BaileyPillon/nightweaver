# Nightweaver 0.19.2 notes

0.19.2 is a fix release for the `antigravity` provider. 0.19.1 added the kind without ever having seen a successful `agy` run, and an `agy` reviewer was then reported to return an empty answer. This release is built on the first signed-in runs: nine small deliberate ones of `agy` 1.5.17 on 2026-11-25, driven exactly as Nightweaver drives it (`--input-format stream-json --output-format stream-json`, no `--print`, the task on stdin as one user message), against a scratch repository of two files with one seeded bug. Fourteen live agent turns were spent in all: nine deliberate, and five unintended ones when a shell rewrote `/permissions` and similar slash commands into file paths, which `agy` then took as ordinary chat prompts. Writing this release spent no further turn: the two permission listings it uses are a slash command that `agy` answers without a model.

The tests replay the captured streams (`tests/agy_streams`, with conversation ids and local paths replaced). None calls a model.

## The mode of each role

Every role runs `--mode accept-edits`, passed explicitly so that agy's own default (`auto`, which silently falls back on this host) never decides.

| Role | `--settings` deny rules | `--json-schema` | Answer taken from |
| --- | --- | --- | --- |
| worker | none; keeps `--disable-slash-commands` | none | its edits; its prose is not used |
| reviewer | yes | reviewer | `structured_output` |
| judge | yes | judge | `structured_output` |
| replanner | yes | wave | `structured_output` |
| directions | yes | directions | `structured_output` |
| comparison, ranking | yes | comparison, ranking | `structured_output` |
| diagnosis | yes | diagnosis | `structured_output` |
| planner, brief | yes | none (JSON in prose) | `response`, else the last message with text |
| probe (`doctor --live`) | yes | none | `response`, else the last message with text |

The rules are `write_file(*)`, `write_file(/)`, `write_file(.)`, `command(*)` and `mcp(*)`, in a file under the runtime's `provider-temp` folder. The first four are the set runs 06 and 08 used: `edit_file` and `write_file` steps both ended against the `write_file` rule, and `run_command` against `command`. `mcp(*)` is agy's documented rule form for MCP tools and has not been run.

Why:

- **Deny rules are the only barrier shown to work.** Run 07 is the control: the same prompt with no rules wrote the files.
- **Plan mode is not a barrier.** No repository write was seen under it, but none was attempted, so that proves only that the model obeyed. For a task-like prompt agy answers in plan mode with an `implementation_plan.md` and a summary, not the JSON the role asked for. A reviewer or judge prompt that sounds like work can therefore end without a verdict, which fits the report of an empty answer.
- **`--sandbox` restricts terminal commands only.** Run 07 edited through it. **`--mode auto` is unusable here.** It falls back to the default mode on a host with no terminal sandbox, and would approve workspace edits on a host that has one.
- **The plan file is not read as an answer.** It is a plan to make edits, so parsing it as a verdict would turn "agy planned a fix" into a review. The parser records the path from the stream, by conversation id and never by newest file, and a failed call names it.
- **`--disable-slash-commands` is not passed to read-only roles.** It was needed only because plan mode ran through slash command expansion. It has never been tried beside `--settings`, so a read-only prompt that starts with `/` is prefixed with `Task:` instead.
- **`toolPermission: strict` was not used.** It might hold edits for approval that a headless run cannot give, but it was not tried and may hold reads too.

## What keeps a read-only role read-only

Four layers, most direct first. The deny rules are the barrier; the rest catch a rule that did not hold.

1. **The rules loaded.** agy loads a rule whatever its class is called (`bogus_tool(*)` loads, and only the admin-only `unsandboxed(*)` is dropped), so a misspelt class would fail open. Before a read-only role starts, Nightweaver runs `agy -p /permissions --settings FILE` in the folder the call will run in (about five seconds on the test machine, no model turn) and does not start the role when agy lists the rules without ours (`configuration`, with the remedy). A check agy cannot answer, or one that would be a model turn because agy's own settings turn slash commands off, lets the call go on. A clear check is remembered for five minutes, per folder. This proves the file reached agy and was applied. It cannot prove that every class name means something.
2. **The stream.** A read-only call whose stream shows a completed step of any writing tool is refused as `read_only_violation` and its answer discarded, whatever the exit code (the tools and the exemption for agy's own folder are under "Review fixes" below). A refusal under a deny rule is a tool step in state `ERROR`; the rules held, but see "Refused, then answered" below for what the call is then worth.
3. **The snapshot check.** The run compares the worktree's tree before and after a review. A test lets an `agy` reviewer edit `result.txt` during its review, the way run 07 showed agy editing: the run records `snapshot_changed`, returns to its checks, the edit fails them, the worker repairs the file and a second review passes, and the accepted commit holds the worker's file. The check detects; it does not undo. An edit that still passed every check and a fresh review would be part of what is promoted, and after a `read_only_violation` the worktree keeps the edit until the run is resumed and re-checked, so the block message tells the operator to look at it.
4. **Nightweaver's own confinement.** Writes stay in the run's worktree.

## The stream

The parser (`agy_stream`) reads the shape agy 1.5.17 writes, and keeps its tolerant fallbacks (fields beside the event name, missing fields, a stream cut off before its result).

- `init`: `conversation_id`, `init.model` (the model asked for with `--model`; absent without it), `init.json_schema` (with a schema), `init.tools`, `init.permission_mode` (the `toolPermission` setting, not `--mode`).
- `step_update`: `conversation_id`, `step_index`, `state` (`ACTIVE`, `DONE`, `ERROR`), `step_type` (`user_input`, `agent_response`, `tool`, `system_message`, `finish`). An `agent_response` streams `text_delta` chunks (`ACTIVE`); its `DONE` event holds the last chunk, or the whole text when none was streamed (run 04), with that step's `usage`. A `tool` step has `tool_name` and `tool_info` (`parameters`, `output`, or `error`). A synthetic `user_input` step after an answer is agy's reminder to fit the schema.
- `result`: `conversation_id`, `status`, `response`, `structured_output` and `json_schema` (with a schema), `num_turns`, `usage`. A success has no `finished_reason` (agy documents one on a failure); a failed turn writes `status` ERROR and `error`.
- **The answer.** A role with a schema takes `structured_output`: agy re-asks until the model's answer fits, and `response` joins every message of the run (narration included, the JSON twice after a re-ask). Any other role takes `response`; when that is blank too, the last agent message with text, so a final message with none (after a tool call) does not hide an earlier one. A subagent's words (another conversation id) are not the answer.
- **Usage** (`input_tokens`, `output_tokens`, `thinking_tokens`, `cache_read_tokens`, `total_tokens`): the total is input plus output, with the thinking tokens inside the output and the cache reads apart. On a fresh call the sum of the steps' usage equals `result.usage` (eight of eight captures). On a resumed call `result.usage` is the whole conversation (run 09: 20,759 against 5,735 for the call), so 0.19.1 counted the earlier call's tokens again on every `--conversation` call. A call now counts the sum of its own steps' usage, and falls back to `result.usage` when no step reported any. A stream cut off by a timeout still counts the steps it finished. `result.duration_seconds` is also wrong on a resume (99 s for a 12 s call) and is not used.

## Failures

A read-only role that finishes with status `SUCCESS` and nothing to read now fails as `ProviderUnavailable` kind `no_answer`. The message gives the role, the status, how many agent messages had text, whether a structured answer was missing, the actions agy refused under the rules and any `implementation_plan.md` it wrote instead, and the log. The engine retries `no_answer` like a transient failure (the reviewer or judge fallbacks first, then `retry.transient_attempts`), charges no attempt to the worker, and then blocks with that message. Every caller shows it: the run's `last_error`, the planner's and brief writer's errors, and `doctor`. A worker's empty prose is not a failure. The three callers that already answer an unreadable reply themselves are the exception (see "Review fixes, round 2").

The other new kinds: `read_only_violation` (not retried; fallbacks first, then the run blocks), `read_only_refused` (see "Review fixes"; retried like `no_answer`) and `configuration` for rules agy did not load (the existing kind, shown with its remedy).

## doctor

`doctor --live` runs the probe in the configuration the roles use (`--mode accept-edits` and the deny rules; the schema is the only difference from a reviewer), and asserts a non-empty `READY`. The report adds `read_only_rules`: `enforced`, `missing` or null. A route whose agy did not load the rules is blocked before any model call. A probe that answers `READY` while `read_only_rules` is null is `unverified` (see "Review fixes"). A probe that returns nothing is blocked as `no_answer`; for the other providers a clean exit with nothing in it is now `empty_answer` instead of `unexpected_response`.

### Refused, then answered

0.19.2 called refusals expected and accepted the answer that followed. That is changed: `invoke()` returns only the code, the session and the answer, so an accepted answer loses the signal, and the engine would send a REVISE that describes refusals to the worker as "Independent review requested changes". The cost is a retry and, in the worst case, a blocked run for a role whose refusal was harmless: a reviewer that always wants to run `git diff` blocks after the retries instead of being accepted without it, and the remedy is the prompt or the route. Of the skeptic's four live calls, one had refusals, and it was the audit prompt built to provoke them.

### The read-only note

The role prompts say only "Remain read-only; do not edit anything." They never say that shell commands are unavailable, so an `agy` reviewer on a repository with Python gate scripts may try to run one, be refused under the deny rules, answer anyway, and have the answer discarded as `read_only_refused`. `invoke()` now puts a short note in front of the prompt of every read-only `agy` call (every call that gets `--settings`), inside the same stream-json user event: "This call is read-only. Every file write or edit and every shell or terminal command is denied, and an answer given after a denied attempt is discarded. Use only read tools: read files, list folders, search. Everything you need (the task, diffs, check results, logs) is in this prompt or in files you can read." It is followed by a blank line and the unchanged prompt. The worker's prompt and the other providers' prompts are not touched. The note starts the message, so a prompt that begins with `/` can no longer run as a slash command; the `Task:` prefix stays as a guard anyway. The note is a hint, not a barrier: the deny rules and the checks above still decide what is refused, and no real `agy` call has yet shown whether the note stops the attempts. `test_release_0192_agy_note` (11 tests) covers where the note goes and where it does not.

### Not done

- No deny rule for `invoke_subagent` or `browser_subagent`: a rule class that has not been run live loads whatever it is called, so it would prove only that the file reached agy.
- A writer step still `ACTIVE` when a stream is cut off (a timeout) is not counted: the call has failed anyway and the snapshot check sees the tree.
- No real agy call was made to test these fixes.
