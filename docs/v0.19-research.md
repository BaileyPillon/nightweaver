# Nightweaver 0.19 · Goal pursuit

Version 0.18 recovered a run after its runner died. It did not make a run finish a goal. An audit of 118 runs on one machine, 13 of them real work, showed that the most important loop, choosing the next piece of work, judging progress and deciding when to stop, was a person. Version 0.19 moves that loop into Nightweaver. It adds a design-direction tournament, a plateau rescue, a one-line `wish` entry point, an interaction sweep for browser gates and opt-in phone notifications, and it fixes ten defects that the same audit found in the repair loop, the runtime and the browser path. The release then went through an adversarial review, one live trial and one blind head-to-head. All three are described below with their limits. The head-to-head is one brief and one build per contender, so it is one data point and not a general result.

## Why this release

The audit read 46 run databases holding 118 runs and 4,039 events, 2,270 of them excluding heartbeats. It also read 67 messages from the owner, planner logs and worker and reviewer evidence logs. Thirteen of the runs were real work with real models and no scripted worker. The rest were benchmark trials, release fixtures and early smoke tests, counted separately so fixtures do not inflate the success rate.

- **There was no outer loop.** 24 of the 67 owner messages were the person acting as the loop: nine were some form of "keep going" and fifteen repeated the same "research and implement the top ten" prompt. `goal` asked the planner for a plan once and nothing re-planned afterwards. A real run was one fixed plan of one to three milestones lasting two to 43 minutes.
- **It was not unattended.** 8 of the 13 real runs needed a human step-in after launch: a missing Git identity, a verifier bug, a logger crash, visual review, a stalled worker, authentication and an infeasible brief that had to be rewritten.
- **The newest real run failed in the open.** The CROW run produced zero accepted milestones in 34 minutes and 29.2 million reported tokens, about 12.7 million after correcting a counting error. Its only check confirmed that a report file existed. Its brief contradicted itself. The repeated-failure detector did not fire, and its third attempt changed nothing but was reviewed anyway.
- **Time went to workers.** Across the live runs, workers took 70% of the time, reviewers 15%, a local advisory model 4% and checks 2.6%. Only 48% of worker and reviewer time landed in an attempt that ended up accepted.
- **There was no head-to-head evidence that a OneShot beats standalone Codex or Claude Code.** The only matched run with the same model was a trivial Unicode search task. Both accepted it. Nightweaver took about 2.8 times as long and 4.8 times the tokens (n=1). The 35-run "head-to-head" pilot mostly measured AGTX, and every Claude cell in it was blocked by authentication. The one measured advantage was stronger acceptance gates catching false passes, and the standalone agents were never given the stronger gate. The long multi-milestone runs (24 to 43 minutes) had no standalone baseline, which is where orchestration ought to matter. Cost could not be compared, because usage telemetry was missing for some contenders and inflated for resumed Codex sessions. This release adds an outer loop and fixes defects. It then ran one matched comparison, the [blind head-to-head](#blind-head-to-head) below, which is still n=1.

## Research coverage

The review window for outside material was August 21 through November 21, 2026, and the local baseline was the 0.18 release at `a4c764e`. Four inputs fed the rankings.

**Field evidence.** Read-only queries of the 46 Nightweaver run databases found on the machine, the planner logs, the evidence logs of the CROW run, the project's earlier research notes and the owner's messages. Fixed-in-release statements come from commit history and the assistant's commentary, not from re-runs. Operator step-ins are inferred from run events plus that commentary. The cumulative-token explanation is inferred from log structure, not from provider documentation. Subscription-window effects are not visible in the run databases. The CROW run still in progress at the time is not counted.

**GitHub, Hacker News and blog research.** Issues, releases, READMEs and the search API on GitHub, Hacker News through its search API and thread pages, arXiv abstracts, vendor documentation and changelogs, and engineering blogs. Page text passed through a small summarizer, so numbers may be slightly off, and items seen only as search snippets are marked. This was a scoped search of publicly discoverable material.

**Literature.** arXiv, OpenReview and conference papers from 2025 and 2026, plus engineering posts from Anthropic, OpenAI, Cursor and METR, weighted to the last six months. Most studies use small or older models, planted bugs, or math and language tasks, so transfer to frontier coding agents and web interfaces is limited. Where a source says so, this document says so.

**A GitHub consensus pass and an X pass.** A later pass sampled 1,704 unique GitHub issues created since August 21 (the top 200 or so by reactions in each of three vendor CLI repositories, the top 100 in eleven harness repositories and 14 keyword searches). It surfaced about 660 repositories with 72 searches, fetched 53 READMEs, about 45 of them read in condensed form, and read Claude Code's changelog (73 releases). No repository was cloned or run, and source code was not read. Reactions are a GUI-user signal and autonomy requests rarely pass 30, so themes are lower bounds with fuzzy borders. Stars are a weak signal here (one repository with 308 thousand stars has 167 open issues, and five repositories created on one day sit at about 500 stars each and look farmed), so a mechanism is weighted by how many independent repositories converged on it. Thirty-day star gains come from parsed charts and are good to about 3 to 5 percent. The X pass read individual public posts and X Articles through a mirror API, plus search-result titles, with the same summarizer caveat. YouTube was seen only as titles.

**Reddit was not read.** It was blocked in the built-in browser and in the web search and fetch tools, and a third-party mirror returned one low-signal query before refusing further requests. An attempt through the Chrome extension failed twice because the extension was not connected, and then stopped. Reddit appears only as about 15 thread titles relayed by Hacker News, with no comments or vote counts. The Reddit communities for Claude, Codex, local models and agents are not covered, and no Reddit consensus exists. User voice in this release is GitHub issues, Hacker News and individual X posts.

In the tables below, *preprint* marks a single arXiv study to treat as a strong hint, *vendor-reported* marks a figure from the vendor's own post, *user-filed* marks a GitHub issue that is one person's account, and *unverified* marks a claim seen only as a snippet or contradicted elsewhere.

## Top 10 issues fixed

| Rank | Defect | Fix | Evidence |
|---:|---|---|---|
| 1 | No goal-level loop. A run ended when its plan was exhausted, and a person chose what came next. | The last accepted milestone moves the run to judging. A judge scores the build and a planner adds waves until the goal is met or a stop rule fires. Every stop has a typed reason. | 24 of 67 owner messages were the person acting as the loop. [Harness-of-Harness](https://arxiv.org/abs/2609.01481) (preprint, its own benchmarks). |
| 2 | The repeated-failure detector never fired. It hashed the reviewer's wording, so any paraphrase reset the count. | A failure is identified by phase, sorted failed gates and build tree, never by wording. The third identical failure stops the run with a stated cause. | 0 `repeated_failure_stopped` events in 118 runs. One run rejected the same "10/11 checks passed" output twice and logged a count of 1 both times. [Review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/) on round caps. Small models reproduced a near-identical program in 33–68% of conditioned retries ([preprint](https://arxiv.org/abs/2607.26117)). |
| 3 | An identical build tree was reviewed again. | A worker that changes nothing after a review rejection is stopped as `no_progress` without re-running checks or the reviewer. | 4 | A usage limit blocked a run within seconds. | The provider's reset time is parsed and the run parks until 90 seconds after it, then resumes on its own. ## Top 10 verification and integrity changes

These changes make a wrong answer harder to accept. Most came from the adversarial review or from the live trial.

| Rank | Change | Effect | Evidence |
|---:|---|---|---|
| 1 | The judge scores against one fixed rubric and is never told `target_score`. | The controller applies the threshold. No prompt shows it. | In the live trial the judge's prompt stated the target of 88 and the judge returned 88. A no-target scoring of the same build in the head-to-head gave 88 (Opus) and 94 (Astra), on different evidence, so the trial's 88 is neither proved nor ruled out as anchoring. In-band judges accepted real regressions 44% of the time ([preprint](https://arxiv.org/abs/2607.25152)). |
| 2 | A judgment that would finish the run is confirmed by a second, independent one. | A fresh session sees the same build, the screenshots in reverse order and no first verdict. `MET` stands only at `target_score - confirm_margin` or better. Otherwise it continues as `NOT_MET` on the lower score. | A second model found different errors, with 41.2% overlap ([preprint](https://arxiv.org/abs/2610.01471)). It costs one more judge call when a run would finish, and a confirmation the budget cannot fund is recorded as skipped. The default confirmation uses the judge's own route. It has not run live. |
| 3 | Verdicts fail closed. | An answer with disagreeing or malformed verdict objects is unreadable, not resolved to a favorable one. | A blocker in the review: a trailing or earlier verdict-shaped object overrode the real verdict. |
| 4 | Credentials are scrubbed by name from gates, git, suite adapters and `command` routes. | Worker-written test code cannot read a token. Key-shaped tokens are masked in gate logs. `inherit_credentials` is an explicit opt-in for a route that needs one. | The same defect was reported three times, once of them as a blocker: gates ran with the Claude token, and a Codex worker could write a test that posted it. Outside reports: [auto mode is not a security boundary](https://embracethered.com/blog/posts/2026/breaking-claude-code-opus-5-and-automode/), and ["Don't Ask Again" leaked secrets into public repositories](https://news.ycombinator.com/item?id=50407882) (unverified). |
| 5 | Tool droppings are deleted from the worktree. | No check passes on a file the accepted commit lacks. | A blocker in the review. See issue 9. |
| 6 | Keep-best ranks builds by whether every ledger check passed, then by score. | A build that fails its own checks never replaces a green one. | The review found a failing build winning on score alone and the green build being discarded (major). |
| 7 | A revert is decided and saved before the result branch moves, and finished after a crash. Discarded milestones are reported as discarded everywhere. | A crash between the judgment and the revert leaves a consistent branch. The milestone-limit stop restores the best build. | Three minor findings: the ref moved before the judgment was saved, the 50-milestone stop left the latest build, and `handoff`, `fork` and `replay` still listed discarded milestones as accepted. |
| 8 | Comparisons are read in both orders. | A rescue strategy qualifies only by scoring more than half the points over a pair the judge read in both orders. The tournament reports position bias. | Position consistency under swap was 83 to 90% for the judges in [WebDevJudge](https://arxiv.org/abs/2510.18560). In the head-to-head neither judge was position-biased on any of three pairs. |
| 9 | The interaction sweep is contained. | Writes and cross-site navigations are answered locally, destructive and submit controls are skipped, every question put to the page has a deadline, and coverage is reported. | The sweep's own review upheld 22 findings, all fixed. |
| 10 | Smoke gates fail closed. | A repository with tests discovery cannot run keeps the no-suite failure instead of getting a smoke gate. The `Visual smoke` gate is added only if it passes on the committed baseline. A `visual_match` gate never falls back to another browser. The favicon exemption is narrow. | A blocker in the review: the smoke gate silently replaced the no-suite failure for repositories with tests in unrecognised ecosystems. Three more major findings on new repositories, site roots and the Edge fallback. |

## Operating a pursuit

```powershell
nightweaver wish C:\src\project "Make the pricing page feel finished" --preview
nightweaver oneshot C:\src\project "Build a polished pricing page" --pursue --judge claude --judge-model claude-opus-5-5 --judge-effort xhigh --waves 3 --wait
nightweaver pursuit RUN_ID
nightweaver pursuit RUN_ID --add-waves 2
nightweaver report RUN_ID --output report.html
```

The judge is the part to watch. A judge from the worker's vendor is allowed but recorded. `target_score` defaults to 85 (88 for a wish) and `plateau` to two judgments that fail to beat the best. A stopped run keeps its best build on `nightweaver/<run-id>`, and `--add-waves` resumes it at the planner, from the best build's gaps, with a fresh plateau count. Every judge scores against one fixed rubric and is never told `target_score`, and a judgment that would finish the run is confirmed by a second independent judgment (`confirm`, `confirm_margin`). Each wave costs a planner call, a worker call per milestone, a judge call and, for the judgment that finishes the run, a confirmation call. Exploration and rescue add worker and judge calls on top. In the live trial a four-milestone wave took 16 provider calls and 70.6 minutes. Set `budgets` when spend matters. The README has the `pursue` block, the unattended-run settings, the Claude token setup and the notification privacy note.

## Adversarial review

A first adversarial review covered pursuit, the runtime, the repair loop, the browser path, notifications and compatibility with saved 0.18 state. It put 53 candidate defects to skeptics. Each candidate went to three skeptics, whose task was to reproduce it or refute it. 51 were upheld and 2 were refuted. 49 of the 51 were confirmed by all three skeptics and 2 by two of the three.

| | Count |
|---|---:|
| Candidates | 53 |
| Upheld | 51 |
| Refuted | 2 |
| Upheld by severity | 6 blocker, 21 major, 24 minor |
| Upheld by area | runtime 10, pursuit 10, notifications 10, compatibility with saved 0.18 state 9, repair loop 6, browser path 6 |

Six defects were found from two or three angles each: credentials reaching gates (three findings), failure fingerprints computed on the unfiltered tree (three), `git_timeout` not applied after a restart (three), the idle watchdog on saved 0.18 plans (two), Claude sessions resumed under another config directory (two) and wave paths not given to the planner (two). The 51 findings therefore describe about 42 distinct defects. The six blockers were the credential leak (three findings), tool droppings letting a check pass on a file the commit lacks, a verdict parser that failed open, and a smoke gate that replaced the no-suite failure.

All 51 were fixed in five fix groups: pursuit (judge anchoring, confirmation, keep-best, reverts, scoped waves, stops), repair loop and engine (fail-closed verdicts, droppings, reviewer failures, git timeouts), browser and discovery (smoke gates, site roots, favicon), credentials with Claude sessions and usage-limit classification, and notifications (terminal stops, quiet hours, shared state, plain messages). Each fix was then attacked again by two skeptics, which reproduced further gaps that were fixed in follow-up commits. Examples are malformed verdicts and droppings inside a folder a milestone names, a confirmation budget and stored discards, a notification release after quiet hours, and Visual smoke gaps in `wish`. The interaction sweep and the plateau rescue were reviewed separately: 22 upheld findings for the sweep and 10 for the rescue, all fixed.

Limits. The skeptics are language-model agents, so an upheld finding means three of them reproduced it, not that a person did. The findings cover six areas, and none is in the exploration tournament. No review record for it was available when this was written, so treat it as the least reviewed feature. A review finds defects. It does not show their absence.

## Not in this release

- **Pursuit UI and UX.** The dashboard names pursuit events in plain words, but it cannot start a pursuit, an exploration or a wish. It has no score curve or target-against-current view, and rescue and exploration events appear under their event names. That waits for an options round with the owner before anything is built.
- **Owner choices and the phone inbox.** Notifications ship. The decision inbox exists as library calls that send a question with up to three buttons and read the answer, but no run asks the owner anything. The tournament's `owner_choice` hook still returns no choice, so the judge alone picks the design direction, and nothing sends the owner two finalists.
- **Held-out checks and tamper detection.** Not built. A builder can still see every visible check. `protected_paths` guard tracked checks, and the fixed rubric and the confirmation reduce judge anchoring, not test gaming. The trap study in the coverage table is why this stays on the list.
- **Quota-aware failover, a toolchain lock and a CLI canary.** Not built. A usage limit parks the run until reset. Switching vendors on a limit, pinning each run's toolchain and probing the CLIs before a wave were ranked highly in the GitHub pass, on the researcher's own scoring. Served-model logging covers only the model half of drift.
- **Parallel candidates.** The tournament and the rescue build their candidates one after another, not in parallel, and only before milestone 1 and at a plateau. Evidence for blanket parallelism is weak (see the coverage table), and a single-task experiment found a tournament cut input tokens by 67% against four sequential retries ([DEV post](https://dev.to/tappers_/escaping-sunk-cost-retry-loops-in-coding-agents-single-session-retries-vs-a-parallel-best-of-n-3p3i), one toy task).
- **Judge calibration to the owner.** Keep-best compares absolute scores from separate calls. Pairwise judging in both orders is used only in exploration and rescue. There is no golden set of owner-labelled pairs to calibrate the judge or to measure its agreement with the owner.
- **A Reddit consensus.** Not gathered. Reddit could not be read (see Research coverage). Re-run that pass once the Chrome extension is connected. The GitHub consensus was gathered.
- **A repeated benchmark.** The head-to-head is n=1, with one brief, one build per contender and no repeats, so run-to-run variance is unknown. Its judges are LLMs from the builders' families. A fair repeat needs more briefs, repeated runs, a human panel and a standalone Claude contender that is allowed a shell.
- **Live trials of the later features.** Waves after the first, keep-best reverts, the rescue, exploration, the sweep, the confirmation, `wish`, usage-limit parking and notifications were not part of the live trial or the head-to-head. Their tests use scripted workers, mocked providers and test pages, and their value in a real run is unmeasured here.
- **Lessons memory.** Unconsolidated memory eventually fell below a no-memory baseline in [Hippo](https://arxiv.org/abs/2610.24453), and reused memory caused regressions in [MemDev-Bench](https://arxiv.org/abs/2610.27524) (both preprints). A wrong note that gets trusted can loop an agent ([Anthropic on agent memory](https://anthropic.com/engineering/components-of-agent-memory)). A design that stores lessons with evidence and applicability conditions comes first.

## Live trial

Run `5b4ec27ab2d5` built **Ukiyo Harbor**, a single static web page showing an animated Edo-period woodblock print of a harbour with a four-time-of-day control, from a repository that held only a README. The brief asked for seven things: a local-only page, a recognisable ukiyo-e look, a dusk harbour composed for 1440x900 and 390x844, a keyboard-operable time-of-day control, gentle motion that stops under reduced motion, accessible controls, and a finished feel.

Setup: Codex `gpt-6.2-astra` at `xhigh` as worker, Claude `claude-opus-5-5` at `xhigh` as milestone reviewer and goal judge, a local `qwen3.8:27b` advisory model, DeepSeek `deepseek-v4-pro` as planner of the four milestones, one `Browser smoke` check, `max_waves` 3, target score 88, a budget of 60 calls and 4 hours. The data come from the run's event log, opened read-only.

| Measure | Result |
|---|---|
| Wall time | 70.6 minutes (4,234 s) from `run_started` to `run_completed` |
| Milestones | 4 accepted in one wave, with 5 worker runs |
| Reviews | 5, with 1 rejection (milestone 3, attempt 1) |
| Provider calls | 16: 5 worker, 5 reviewer, 1 judge and 5 advisory |
| Goal judgment | `MET` 88/100, 7 of 7 criteria met, 6 gaps listed, on the first wave. The judge saw 2 screenshots |
| Tokens | 19.4 million observed on all channels, of which 1.63 million were not cache reads |

**The rejection.** The reviewer rejected milestone 3 because the smoke check had no steps, so its only screenshots were the first load at each viewport and could not show the four palettes. It called the code largely sound and named an evidence gap. The worker resumed in the same session, added a reproducible Playwright test and the next review passed. That cost about 10 minutes of worker time and one more review. This is the case the interaction sweep was built for.

**What the judge said.** It marked all seven criteria met, scored 88 and still listed six gaps. One was that the dusk sun sits mid-sky although the goal asks for a low sun, and one that the palette change is an instant swap, not a re-inking. The judge saw two stills and judged motion from source.

**Honesty notes.**

- The judge's prompt stated the target score (88) and the score equalled it. That is an anchoring flaw. A model told the pass mark can return it. The release fixes it with a fixed rubric, no target in any judge prompt and an independent confirmation before `MET`. A later no-target scoring of the same build by the same model gave 88 as well, but on different evidence (nine fixed captures and a fact sheet), so it neither confirms nor rules out anchoring in this run.
- The run did not use any waves after the first, keep-best, the rescue, exploration, the sweep, the confirmation, `wish`, usage-limit parking or notifications.
- One run on one goal. It shows that the loop can finish a task end to end. It does not show a success rate.

## Blind head-to-head

The finished Nightweaver build was compared with two standalone builds of the same brief: Codex alone (`gpt-6.2-astra`, `xhigh`, one session) and Claude alone (`claude-opus-5-5`, `xhigh`, one session). The numbers below come from the comparison's own results file.

**Method.**

- **Blind labels.** The three builds were copied from their commits into folders labelled A, B and C with source only (README, evidence and tests left out). The label mapping was fixed before judging, kept out of the judges' reach, and a leak scan found no build or vendor names.
- **Identical capture.** One script drove every build the same way in a headless Edge: first load at 1440x900 and 390x844 (plus a touch-emulated phone load), each time of day by clicking the control, a keyboard-focus shot, then measured facts such as requests, errors, overflow, keyboard walk and motion with and without reduced motion. Nine screenshots per build.
- **Two judge families, both orders.** `claude-opus-5-5` and `gpt-6.2-astra`, both at `xhigh` and both served as requested, read the same screenshots, fact sheet and source, read-only. Every pair was judged twice with the presentation order swapped. A pair counts as won only when both orders pick the same build, and none disagreed.
- **Fixed rubric, no target.** Each build was also scored alone against the same seven criteria, with no target score mentioned.

**Results.**

| Measure | Nightweaver | Codex alone | Claude alone |
|---|---:|---:|---:|
| Pairwise calls won (of 12, both judges, both orders) | 8 | 4 | 0 |
| Pairs won (of 6) | 4 | 2 | 0 |
| Absolute score, `claude-opus-5-5` | 88 | 89 | 86 |
| Absolute score, `gpt-6.2-astra` | 94 | 92 | 86 |
| Mean absolute score | 91 | 90.5 | 86 |
| Objective checks passed (of 10) | 10 | 10 | 10 |

Nightweaver's build won all 8 pairwise calls it was in, 4 of 4 against each standalone build. Neither judge was position-biased on any of its three pairs. Both judges ranked the Claude-alone build last. On the fixed rubric the three builds sit in the same "finished" band, 86 to 94. Against the Claude-alone build Nightweaver was ahead with both judges (+2 and +8). Against the Codex-alone build the absolute scores do not separate them: one judge scored Nightweaver one point lower and the other two points higher, so the win there rests on the pairwise calls. The judges credited Nightweaver's graded sky, curling foreground waves and night view, and credited the Codex-alone build with more human detail.

**Cost.**

| Measure | Nightweaver | Codex alone | Claude alone |
|---|---:|---:|---:|
| Wall time | 70.6 min | 16.3 min | 57.8 min (75.3 with a discarded first attempt) |
| Observed tokens, all channels | 19,414,346 | 1,672,637 | 6,731,883 |
| Tokens that were not cache reads | 1,629,445 | 101,437 | 677,367 |
| Reported cost | not measured | not reported | 10.98 USD (list basis) |

As a multiple of each standalone build, Nightweaver took 4.3 times the Codex build's wall time and 11.6 times its observed tokens (16.1 times counting only tokens that were not cache reads). Against the Claude-alone build it took 1.2 times the wall time (0.9 with the discarded first attempt) and 2.9 times the tokens. Its five Claude reviews and goal judgment are estimated at about 10.3 to 13.4 USD, about the whole cost of the Claude-alone build, and the Codex worker's cost is on top and not priced in the evidence. Token units differ between contenders (Claude counts cache writes as well as reads), and the three builds ran at overlapping times on one machine, so wall times include unmeasured contention.

**Limits.**

- n=1: one brief, one build per contender, no repeats. The four pairwise calls per pair come from two judges and two orders on the same two builds and are not independent samples.
- Both judges are LLMs from the families that built the artifacts, and Nightweaver's build carries both families' influence (Codex as worker, Claude as reviewer and judge). Each judge did pick Nightweaver over its own family's standalone build, which argues against simple self-preference, but family bias is not ruled out. Judges might also infer a producer from style.
- Nightweaver's own judge had seen the target and the run was iterated against the same seven criteria that the absolute scores use, so its build was optimised for that rubric. The 88 that `claude-opus-5-5` gave it in the head-to-head equals the run's own 88, from the same model and rubric but not an independent check.
- The comparison mixes orchestration with a second vendor and a reviewer. It does not isolate what the orchestration adds.
- The judges saw nine static screenshots, a fact sheet and the source. They did not watch the motion, so motion quality is judged from measured facts. All three builds passed all ten objective checks, so those checks do not separate them. The re-ink pixel threshold is the analyst's choice.
- The Claude-alone contender ran with shell commands blocked, as Nightweaver's Claude routes do, and logged 12 permission denials. It could not run a browser on its own page, which fits its 24 console warnings (a canvas performance hint). A Claude run with a shell may do better. Its first attempt built nothing, because it loaded the operator's interactive `CLAUDE.md` and obeyed its delegation rules (1,052 s, 1.54 USD). The final attempt is what is compared, with both-attempt figures as a sensitivity check. That failure is why Claude routes now run in an isolated config directory.
- Nightweaver's milestone planning step (4,538 tokens, 33 s) ran before the run started and is outside these totals.
